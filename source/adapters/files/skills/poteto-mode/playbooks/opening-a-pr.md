### Opening a PR

Read the [shared runtime contract](../../../CODEX.md) for delegation, authority, models, history, helpers, and session limits.

Invoked at the end of every other playbook.

Work from a git worktree off the PR's actual base, and keep unrelated work out of it. That is trunk for independent work, and the parent branch's verified tip for a stack child. Inspect Git state first, and never use `reset --hard` or discard unrelated work to get a clean start. One writer owns each branch and worktree. Rebase into small, landable commits. Run the available `deslop` skill over the diff before commit.

Title: `type(scope): subject`, naming a real symbol when one carries the change. Body: a one-minute briefing under 40 lines with these `##` headings in order, dropping empty ones: `## Why`, `## What changed`, `## Scope`, `## Tradeoffs` (only rejected alternatives a reviewer would otherwise ask about), `## Blast Radius`, `## Verification`.

Stack follow-ups by base branch. Open a PR only within the requested scope. Prefer an available purpose-built forge tool when it supports the operation, and never invent one.

**Draft lifecycle.** A PR stays a draft until landing is authorized, unless the user or the repository's rules ask for a ready PR. Every playbook that opens, babysits, hands off, or lands a PR follows these stages. Name the PR by its canonical URL, or by number with `--repo <owner>/<repo>`, in every `gh` read and mutation, and pass `--owner`, `--repo`, and `--pr` to the watcher, because in a fork checkout a bare number can resolve to a different PR. A PR that is already ready skips stage 3 and still goes through stages 2 and 4. When Shipping, an Autopilot owner, or an Autopilot-stack handoff takes over a PR whose landing waits on a verdict, first check whether auto-merge or merge-when-ready is armed, or the PR already sits in a merge queue (`gh pr view <pr> --json autoMergeRequest` plus the GraphQL `isInMergeQueue` field, or `origin pr view <pr>` on Origin), because the forge can land it before the verdict or the pinned merge. If either holds, turn auto-merge off with `gh pr merge <pr> --disable-auto` or `origin pr merge <pr> --disable-auto`, or dequeue the PR, when that is authorized, and read the result back. Otherwise stop and report that the forge can still land it. Standalone Babysit never lands anything, so when the user armed auto-merge or queued the PR, it reports that in its first status line and carries on, and never turns it off unless asked.

1. **Open.** First push the branch to the authorized remote and confirm the pushed head SHA, so creation never prompts for a push destination. Then run `gh pr create --draft --repo <base-repo> --base <base-branch> --head <head> --title <title> --body-file <body-file>`, naming the pushed head explicitly so a fork setup never prompts. `<head>` is `<branch>` when the head is in the base repository and `<user>:<branch>` for a user-owned fork. For an organization-owned fork, which `gh pr create` cannot name, run `gh api repos/<base-repo>/pulls -f base=<base-branch> -f head=<org>:<branch> -f head_repo=<fork-name> -f title=<title> -F body=@<body-file> -F draft=true`. When Origin's CLI resolves the repository, run `origin pr create --draft --base <base-branch>` with the same title and body instead. Omit `--draft`, or send `draft=false`, only when the user or the repository's rules ask for a ready PR at creation; on Origin, pass `--status open` for that, because older Origin clients default to draft. If the forge rejects the draft because the repository cannot hold drafts, as private repositories on GitHub Free cannot, do not retry silently. Open it ready only with the user's authorization, record it as ready only because drafts are unavailable, and keep it out of landing until stages 2 and 4 clear it. Otherwise stop and report. A stack child's base is its parent branch, and on Origin it also passes `--stack-on <parent-pr>`. Read the draft state, the head SHA, and the base, and on Origin the parent, back.
2. **Verified.** The evidence is the head and base, the CI results at that head, and proof receipts. In Autopilot, the owner sends them as a proof report claiming no readiness, and the coordinator audits it before issuing the independent verdict. In standalone Shipping, the independent verifier's receipts and the forge's CI results for the same head and base serve. The PR is verified once the required checks and every gate the user set for before promotion pass at this head and that verdict covers it. A gate that can only clear after promotion, such as a code-owner approval that the forge requests on promotion, is a merge gate for stage 4, not a stage 2 gate; a failing optional check goes in the report and does not block. A draft is then a verified draft. If the head does not contain the base the verdict runs on, the verdict must cover the merge result with that base, or a head rebased onto it, because a head and a base that each pass can still fail together. A later base move carries the verdict only under Shipping step 3's rule. Classify each required check by its trigger. A check whose workflow trigger or rules show that it starts only when a PR becomes ready is deferred to promotion: record it by name, and require it in stage 4. Every other required check must pass on the draft. A failed check lookup is an error, not a deferral. A verified draft is the report a draft gets in place of merge-ready: Babysit and Autopilot owners report it, and Autopilot-stack hands it to the operator with the checks and reviews expected after promotion. A verified ready PR keeps its readiness and is reported with any gates still open.
3. **Promote.** Only a draft that stage 2 verified at its current head, and only when landing is authorized, in Shipping step 4 or Autopilot-full step 5, or when the user asks. Check again for armed auto-merge, as above, because promotion can release it before stage 4's checks. Then run `gh pr ready <pr>` or `origin pr ready <pr>`, and read the PR back as no longer a draft.
4. **Land.** Wait for the checks and reviews that promotion starts. Merge only when the forge reports the PR mergeable with every required check complete. On GitHub, `mergeStateStatus` is `CLEAN` or `HAS_HOOKS`, or `UNSTABLE` when every required check and every gate the user set has passed, in which case report the failing optional check. Treat `BLOCKED`, `BEHIND`, `DIRTY`, `UNKNOWN`, and any other state as unresolved. On Origin, `origin pr view <pr> --checks` reports it mergeable with no blockers. Land one PR per base at a time, so a merge never lands on a base another landing just moved. Right before merging, reread the head SHA, the base repository and branch name, and the base SHA from the base branch's own tip, not a PR field that can lag it. A base branch other than the authorized one stops the landing. If the head or base SHA moved since the verdict, apply Shipping step 3's rule. `--match-head-commit` pins only the head, so the base can still move between that reread and the merge. Right after the merge, read the merge commit's base parent. If it is not the base SHA you reread, report that the PR landed on a base its verdict never covered, and verify the base branch at once. Where the forge enforces an up-to-date branch, or a merge queue whose required checks cover the verified behavior, that race cannot happen. Merge pinned to the head the verdict covers, with a merge method the repository and branch allow: `gh pr merge <pr> --squash --match-head-commit <sha>`, with `--merge` or `--rebase` in place of `--squash` where only that is allowed, or `origin pr merge <pr> --match-head-commit <sha>`. On Origin, name only the lowest open PR of its stack, because `origin pr merge` also lands every open PR below the one you name. Do not arm auto-merge or merge-when-ready, because neither forge documents it as bound to the verified head. On a branch that requires a merge queue, `gh pr merge` can arm auto-merge by itself when a check is pending, so do not run it there. The queue builds a merge group from the latest base and any PRs ahead of it, which the verdict never saw. Enqueue through the GraphQL `enqueuePullRequest` mutation with `expectedHeadOid` set to the verified head only when the repository's required merge-group checks cover the verified behavior, and treat a rejection as a wait. Otherwise hand the PR to the operator.

Read the PR back before you report its status. When the host exposes a PR-attachment tool whose instructions require it, attach the verified URL. Otherwise return the URL and record it in the task trail. Opening a PR does not start a babysit.
