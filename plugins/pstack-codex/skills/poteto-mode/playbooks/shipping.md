### Shipping

Read the [shared runtime contract](../../../CODEX.md) for delegation, authority, models, history, helpers, and session limits.

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge, then verify each PR independently before it lands.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One independent verifier per PR through the selected host adapter, started with no parent history, in a real checkout at the named SHA, runs the change the way a user would with an available project driver, browser/app tool, or PTY harness under CODEX.md, parent against head, and against the merge result with the current base when the head does not contain it, and returns `PASS`, `PASS+NOTES`, or `FAIL` with receipts. Post that verdict to the PR only when review communication is explicitly authorized. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch on a base. Record the head and base SHAs it ran on. A chain rebase moves every PR above it to a new SHA without failing any check, and trunk can move under a PR whose head stays put. Before trusting an older verdict, compare the PR's full diff against its base at the verdict SHA with its diff at the current head, byte for byte with whitespace preserved. `git patch-id` alone is not enough, because it ignores whitespace that can change behavior. Also apply Autopilot-full step 5's test for whether the base change can affect the patch, since an identical diff on a changed base can behave differently. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR through the draft lifecycle in `playbooks/opening-a-pr.md`. Confirm stage 2 at the current head, so draft checks pass before promotion, then stages 3 and 4: promote a policy draft, wait for the checks and reviews promotion starts, which are waits and not something to bypass, confirm the forge's mergeable state, reread head and base, and merge pinned to the head the verdict covers. That head is the verdict SHA, or the current head that step 3 carried the verdict to. If the head or base moved since that check, for example during a wait, apply step 3 again before merging. On Origin the plain command also merges every PR below the one you name, and on GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`origin pr view <pr>` or `gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Do not arm `--auto` (Origin merge-when-ready or GitHub auto-merge), because neither forge documents it as bound to the verified head. After a merge lands, retarget the PR whose base was the merged branch to trunk (`origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's rule decides whether the verdict survives. Merge it through the same stages once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. On GitHub, watch the run with `python3 <PLUGIN_ROOT>/tools/runtime.py tool watch-pr -- --owner <base-owner> --repo <base-repo> --queued-stack --allow-draft` using an active process with bounded waits until it reports `COMPLETE` at the ceiling. Pass the run's PR numbers, bottom-to-top, in `--stack-prs`, and pass the same list each time you restart the watcher. `--allow-draft` keeps the PRs above the frontier, still drafts by policy, from reading as blockers. Each one is promoted in step 4 when its turn comes. If the queued watcher still blocks on an upper draft only because its checks start on promotion, watch the frontier PR alone instead, and treat those checks as expected after promotion. If the frontier itself returns `checks-unavailable`, read the forge's state directly and apply the draft lifecycle's rule for deferred checks. When an optional check fails or stays pending, the watcher's terminal state does not decide. Read the required gates directly at bounded intervals (`gh pr checks <pr-url> --required`, or `origin pr requirements <pr>`), report the optional check, and advance when the required gates and the user's gates pass. On Origin, poll `origin pr requirements <pr>` and `origin pr view <pr> --checks` at bounded intervals, never blocking on `origin pr checks <pr> --watch`, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
