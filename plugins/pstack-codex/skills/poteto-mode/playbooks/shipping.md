### Shipping

Read the [shared runtime contract](../../../CODEX.md) for delegation, authority, models, history, helpers, and session limits.

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge, then verify each PR independently before it lands.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One independent verifier per PR through the selected host adapter, started with no parent history, in a real checkout at the named SHA, runs the change the way a user would with an available project driver, browser/app tool, or PTY harness under CODEX.md, parent against head, and returns `PASS`, `PASS+NOTES`, or `FAIL` with receipts. Post that verdict to the PR only when review communication is explicitly authorized. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. Before verifying, check each PR for auto-merge or merge-when-ready that someone already armed (`gh pr view <pr-url> --json autoMergeRequest`, or `origin pr view <pr>`), because the forge can land it before the verdict. Turn it off when that is authorized (`gh pr merge <pr-url> --disable-auto` on GitHub), or stop and report it.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Before trusting an older verdict, compare the PR's diff at the verdict SHA with its diff at the current head, whitespace included, because `git patch-id` ignores whitespace that can change behavior. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, pinned to the head its verdict covers: `gh pr merge <pr-url> --squash --match-head-commit <sha>`, with `--merge` or `--rebase` where the repository allows only that, or `origin pr merge <pr> --match-head-commit <sha>`. If the head moved since the verdict, apply step 3 first. If trunk moved since the verdict, ask whether its changes can affect the patch, as in Autopilot-full step 5, and verify the merge result before landing when they can. On Origin the plain command also merges every PR below the one you name, and on GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`origin pr view <pr>` or `gh pr view <pr-url> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Do not arm `--auto` (Origin merge-when-ready or GitHub auto-merge), because neither forge documents it as bound to the verified head. After a merge lands on GitHub, retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr-url> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. On Origin, leave the child's parent as it is, because Origin moves its base to trunk and keeps the stack; run `origin stack sync` or `origin stack restack`, then `origin stack push --all`, and never `origin pr edit --clear-stack`. The verdict covers the patch, not its commits, so step 3's rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Auto-merge is not armed, so nothing lands until you merge it. On GitHub, wait on the frontier PR with `python3 <PLUGIN_ROOT>/tools/runtime.py tool watch-pr -- --owner <base-owner> --repo <base-repo> --pr <number> --timeout <seconds>` using an active process, and apply step 4 when it reports `READY`. If it reports `checks-unavailable` because the PR has no checks, use Babysit's forge and review-thread read for that PR instead. After the last merge, confirm the run with one `--queued-stack --status-only` pass, passing the run's PR numbers, bottom-to-top, in `--stack-prs`, and expect `COMPLETE` at the ceiling. On Origin, re-read the frontier PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns, apply step 4 when it is ready, and continue until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
